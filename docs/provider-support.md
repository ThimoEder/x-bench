# Provider support

What each provider can do in X Bench today. Update this list with every change to a provider.

| Mark | Meaning |
| --- | --- |
| ✅ Yes | Works, and was checked in the running app or against the real harness. |
| 🧪 Tested | Built, and covered by the contract suite against a fake, not yet seen in the running app. |
| ❔ Untested | Runs on a path the other providers share, but not yet covered or checked for this one. |
| ❌ Not yet | Missing. The note or ticket says what would add it. |
| ➖ n/a | The harness has nothing to map. |

Claude runs through Claude Code (`claude`) and the Claude ACP adapter (`@agentclientprotocol/claude-agent-acp` 0.101.0, with the small patch in `patches/`). Its config folder and binary come from `~/.x-bench/claude.json`, which the settings page writes.

ChatGPT runs through Codex and the Codex ACP adapter (`@agentclientprotocol/codex-acp` 2.6.0, with the small patch in `patches/`), which starts the installed `codex app-server` (`CODEX_PATH`). Checked against codex-cli 0.166.0 signed in with ChatGPT Plus.

| Start a chat from the model menu | ✅ | ✅ | ✅ | The menu groups models by provider. Grok is the default unless Settings picks another. A provider turned off in Settings is left out. ChatGPT's list is "Default" until Codex has reported its models once, then Codex's models, with the one `~/.codex/config.toml` picks as the default. |
| Chat tab | ✅ | ✅ | ✅ | New chat opens a draft with the grouped model menu. The chat runs in `~/.x-bench/chat` on the picked model's provider, without board rules or the review dock. |
| Stream text | ✅ | ✅ | ✅ | |
| Thinking window | ✅ | ✅ | ✅ | Claude's thinking is a summary (`--thinking-display summarized`). On a long think it arrives a few lines every couple of seconds, on a short one in one piece before the answer. Codex sends a bold heading per reasoning step, as each step ends; the raw reasoning stays with OpenAI. The window shows the newest sentences (Grok, Claude) or the last three steps (Codex), changed at most every 1.5 s. Claude's and Codex's thoughts are timed from when the harness went quiet. |
| Title in the sidebar | ✅ | ✅ | ✅ | `session_info_update`. Codex's titles are cut to their first line, at most 80 characters. The patched codex-acp generates a new chat's title when its first turn starts. |
| Provider tag on sidebar rows | ✅ | ✅ | ✅ | Every row shows its provider as a logo, as a name tag or not at all, as General settings picks (logo by default). A switched chat shows the provider it runs on now, and the tooltip names the earlier ones. |
| Reopen from the sidebar | ✅ | ✅ | ✅ | Claude and ChatGPT sessions come from `~/.x-bench/sessions.json`, reopened with `session/load`. The pane switches at once. Grok's chat shows from its update log while it loads, Claude's and ChatGPT's as stand-in rows. |
| Reopen a chat whose folder is gone | ✅ | ✅ | ✅ | The chat opens to be read, and a card in place of the composer continues it in a new worktree, in the checkout the worktree came from, or in a chosen folder. Claude and Codex load the session in the new folder. Grok shows the chat from its update log, and the app moves Grok's session folder under the new folder before `session/load`. |
| Resume after the agent restarts | ✅ | ✅ | ✅ | The running turn ends with the error, open sessions reload, and queued follow-ups are sent after the reload. |
| Delete | ✅ | ✅ | ✅ | Grok's stored copy goes through `grok sessions delete`, and its session folder with it. Claude's stored copy goes through the adapter's `session/delete`, which the patch makes remove the transcript once Claude Code has exited (as an AIR client, the app would otherwise get it archived). Codex archives the thread. If the harness cannot delete its copy, the app still removes the session and says so. |
| Follow a turn another process runs | ✅ | ❌ | ❌ | Grok reads its update logs. Ticket 130. |
| Switch a chat to another provider | ✅ | ✅ | ✅ | The model menu lists every enabled provider. After a confirmation the chat keeps its id and moves to a session on the new provider, which reads what it missed with its first message. Up to 8k tokens (or a quarter of a smaller window) that is the whole conversation as text: each message in its own tag, and one line per run of tool calls. Past that, or when the confirmation's arrow picks Summarize first, the old model writes a summary (at most 6k tokens) as one last hidden turn of at most four minutes, followed by the last two exchanges with each message shortened to 1.5k tokens. The switch runs in the background behind a busy line in the transcript, which can cancel it, and a message sent meanwhile goes to the new model with the handoff. Without a summary (Skip the summary, an old provider that is off, failed or at its plan's limit, or a summary that fails), a long chat goes as text: the newest entries up to a quarter of the new model's window and at most 50k tokens, with only a message that alone takes a third of that shortened. A provider the chat ran on before picks up its own session with `session/load` and reads only what it missed. Checked Claude to Grok and back, and Claude to ChatGPT, with long chats of tables and Mermaid diagrams. |

## Turn

| Feature | Grok | Claude | ChatGPT | Notes |

| Permissions | ✅ | ✅ | ✅ | Claude's and Codex's first request id is 0. Each card shows Deny, Always allow and Allow once, with the harness's own wording on hover and what Always allow covers in its words under the request. Two choices of the same kind keep the harness's names. A request that comes while a card waits, such as from a second Claude subagent, shows once the card before it is answered. Stop answers the waiting ones as cancelled, and a request the harness withdraws leaves the line. An answer names the request it was shown for, so a second click never answers the card that came up after it. |
| Questions from the agent | ✅ | ✅ | ✅ | Shown as the question card at the end of the chat: single picks, multi-selects, the "Other" box, text, numbers and switches. Several questions show one at a time, with a step count, Back and Next, and go back together on Answer. Claude's `AskUserQuestion` (several questions at once, with a free-text "Other" per question) and Codex's `request_user_input` (in every mode, since the app turns on Codex's `default_mode_request_user_input` feature through the adapter's `CODEX_CONFIG`; its questions required) come as ACP form elicitations. Codex reads that answer from the question itself, so the app moves it there. The server holds back an answer that leaves a required question empty. Skip declines, which Claude and Codex read as skipped. Grok has no skip, so Skip and Stop both answer it as cancelled. Stop cancels it, and so does closing the chat. |
| Approval modes | ✅ | ✅ | ✅ | Grok: Always approve, Accept edits, Plan. Claude and ChatGPT: Ask first, Accept edits, Plan, Auto, Always approve. For ChatGPT these are Codex's presets (read-only, workspace-write, Auto review, full access), and Plan is its collaboration mode. The patched codex-acp lets sandboxed commands in Auto use the network, so board calls to the app run without a Guardian Review, and so does any other network call. Grok starts in Always approve, Claude and ChatGPT in Auto, unless Settings picks another mode for new sessions. Codex forgets its preset when a session loads again, and Claude forgets the thread's approval mode (it comes back on Ask). The app remembers each and sets it again, checked after a host restart. |
| Plan approval | ✅ | ✅ | ✅ | Grok asks with `exit_plan_mode`. Claude and Codex ask through a permission that carries the plan: the Plan tab and the card show it. The card reads the harness's choices as Keep planning, Approve and Approve with the mode it names ("Approve, use auto mode"), and Grok's as Keep planning, Quit plan and Approve. Past two ways to approve, the rest open from the arrow beside Approve. After Codex's plan is approved the approval menu follows Codex back to its preset. Rejecting keeps it in plan mode. A second Grok plan that comes while one waits is answered as cancelled. `/plan` and the approval menu both switch Codex into plan mode. |
| Plan written live in the Plan tab | ➖ | ➖ | ✅ | Codex's `plan_update`: the Plan tab opens when Codex starts writing its plan, fills as it goes, and keeps the plan after approval. It comes back after a reload. Grok writes its plan to `plan.md` and Claude sends it with the approval, so both show it once it waits. |
| Model and effort | ✅ | ✅ | ✅ | Older models fold under More models. Effort levels are kept per model. Claude's effort menu shows the level the session runs on: the one saved for the model in Claude's settings, else Medium. Claude forgets a thread's model and effort when the session loads again, so the app remembers them and sets them again, checked after a host restart. |
| Fast mode | ➖ | Off | Off | Claude's is switched off whenever Claude reports it on, since it bills usage credits outside the plan, and hidden once off. If Claude refuses, the menu stays and the chat says so. Codex's uses the plan faster: it is hidden while off and shows while on, so it can be switched off. A way to turn either on is left for later. |
| On/off options | ➖ | ✅ | ✅ | An option whose only choices are on and off, such as Claude's Ultracode or Codex's fast mode while on, shows as a switch at the foot of the effort menu. |
| Cancel | ✅ | ✅ | ✅ | |
| Queue a follow-up (edit, remove, send now) | ✅ | ✅ | ✅ | A picture sent with a follow-up shows on its row. Grok queues itself. For Claude and ChatGPT the app holds the queue and sends each message when the turn ends. Held messages are dropped, with an error, when the adapter stops or fails to restart. |
| Steer | ✅ | ✅ | ✅ | Claude's `_session/steering`. A steer after the turn ended becomes a normal prompt. Codex's `turn/steer` through the same method: one that finds no running turn starts a turn of its own, which shows as the person's message and ends when Codex says the thread is idle. Claude's steer can carry files. |
| Next step | ➖ | ✅ | ➖ | The default for Claude. The message goes into the running turn at priority `next`, so Claude reads it at its next tool boundary without stopping the current step, or right after its last step in the same turn. Until Claude reads it, it can be deleted or sent now. Stop takes it out too. A queued message can also be edited. |
| Read status of a steered message | ➖ | ✅ | ➖ | Below the bubble: "Waiting", with Copy, Delete and Send now on hover, then "Read" once Claude Code's `command_lifecycle` frame says Claude took it in, or "Not read" when Claude Code dropped it or the turn ended first. "Read" fades after three seconds and shows again on hover. "Waiting" and "Not read" stay. Delete takes the message out of Claude Code's queue (`_session/steering/cancel`, patched in). Send now does the same and steers it again at once, which interrupts the current step. |
| Next-line suggestion (ghost text) | ✅ | ✅ | ✅ | Both adapters send it as `session_info_update._meta.promptSuggestions` after a turn. Claude's is Claude Code's `prompt_suggestion`: not on a session's first turn, and not after every turn. codex-acp asks a small model (`gpt-5.6-luna`) after every turn, on the user's ChatGPT plan. |
| Side question (`/btw`) | ✅ | ✅ | ✅ | Claude uses its own `_session/btw`, added by the adapter patch on top of the SDK's `askSideQuestion`. ChatGPT uses an ephemeral `session/fork`, asks for a tool-free answer in plan mode under the read-only preset, turns off the user's Codex MCP servers and plugins for the fork, and deletes the fork after success or failure. Forks stay out of the sidebar and `sessions.json`. Both answer from the conversation while a turn runs and keep their side history in `~/.x-bench/btw/<id>/btw_history.jsonl`, deleted with the chat. |
| Task suggestions | ✅ | ✅ | ✅ | The host's `x_bench` MCP server with `suggest_task`, passed in `session/new` and `session/load`. The tool's line goes in Grok's rules and in Claude's and Codex's appended system prompts. Claude runs it through `allowedTools`. |
| Browser pane tools | ✅ | ✅ | ✅ | The same `x_bench` MCP server adds the `browser_*` tools, with their line in the same places. Opening a site and acting on a page ask in the app's permission card, except in Auto and Always approve. Claude runs the tools through `allowedTools`, so it never asks itself, and its Auto classifier does not see them. Codex gets them with `approval_mode = "approve"` in its config for the server (through the server's `_meta`, which the patched codex-acp passes on), so it does not ask either. Grok sends no picture with a tool result, so its screenshots do not show in the transcript. The agent still sees them. Desktop app only. Builder chats only. |
| Pull request status | ✅ | ✅ | ✅ | The same `x_bench` MCP server adds `pr_status`, with its line in the same places. It reads, so it runs without asking. |
| Chat folders | ✅ | ✅ | ✅ | The same `x_bench` MCP server adds `list_chats`, which reads and runs without asking, and `move_chats_to_folder`, which asks in the harness's own permission card. Both work on the calling chat's project. |
| Routine tools | ✅ | ✅ | ✅ | The same `x_bench` MCP server adds `routine_list`, `routine_create`, `routine_update` and `routine_delete`, with their line in the same places. They check a routine the way the Routines page does. Listing runs without asking. Creating, changing and deleting ask in the app's permission card, which shows the whole prompt and what a change sets, except in Auto and Always approve. Creating or changing a routine whose runs start in Always approve asks in every mode. A routine that changed while the card waited is left alone. Neither Claude nor Codex asks for them itself, as with the browser tools. |
| Simulator tools | ✅ | ✅ | ✅ | The same `x_bench` MCP server adds the `simulator_*` tools for iOS simulators and Android devices, with their line in the same places. Two-finger paths work on both platforms. Acting tools ask in the app's permission card, except in Auto and Always approve, and neither Claude nor Codex asks for them itself, as with the browser tools. Grok's screenshots do not show in the transcript, as with the browser tools. All three read the screen's tree by default and take screenshots only to judge how things look; taps, typing, swipes and button presses answer with the screen's controls. `simulator_steps` runs a known sequence of actions in one call, asks once for the whole list and answers with the whole screen. Builder chats only. |
| Board rules on the system prompt | ✅ | ✅ | ✅ | Claude's are appended to Claude Code's own prompt, on every new session and every load. Codex's go in ACP's append-mode `systemPrompt`, which the adapter adds to Codex's developer instructions, on every new session and every load, so Codex names the thread after the first prompt. Older sessions hold the rules in their first prompt, and the transcript and title leave them out. |
| Board rules for a chat open when its folder gets a board | ✅ | ✅ | ✅ | The rules go with the chat's next prompt that starts a turn, once, inside `<x-bench-board-rules>`, which the transcript, Grok's queue and the title leave out. A load does not help: Claude Code and Codex keep a resumed session's system prompt from its start, and Grok takes rules only at `session/new`. Checked against all three. |
| Board threads | ✅ | ✅ | ✅ | New chat in a ticket's detail opens a sheet with the prompt, model and effort. Its model menu picks the provider, and the chat starts in the background. |
| Routines | ✅ | ✅ | ✅ | A run starts like a suggested task, through the same path for every provider. Checked with all three in the running app: Run now and a scheduled run, each in a new worktree. A worktree run is a git worktree under `~/.x-bench/worktrees`, as for any new session. |
